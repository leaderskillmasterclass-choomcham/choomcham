# ระบบออกแบบหลักสูตรองค์กร

หน้าใช้งาน: `/admin/courses` เชื่อมจากเมนู Admin, Proposal Engine และข้อมูลคำขอ Proposal ใน CRM

## ขั้นตอนทำงาน

1. เลือกต้นแบบ REBORN, COMMUNICATION, TEAM, LEADER, CULTURE หรือ From Zombie to Living Organization
2. หรือเข้าสู่ระบบข้อมูลทีม → โหลดคำขอ → เลือกองค์กร → ออกแบบจากโจทย์องค์กร
3. ยืนยันปัญหา ผลลัพธ์ทางงาน กลุ่มผู้เรียน จำนวนคน รูปแบบ เวลา ข้อจำกัด และกรอบงบประมาณ
4. เขียนวัตถุประสงค์เป็นพฤติกรรมที่สังเกตได้ พร้อมหลักฐาน/เกณฑ์ประเมิน
5. เขียนกิจกรรม เวลา ผลงาน และเลือกวัตถุประสงค์ที่กิจกรรมนั้นรองรับ
6. กำหนดการประเมินก่อน–หลังเรียน การติดตามในงานจริง และผู้รับผิดชอบ
7. เขียนสิ่งส่งมอบ สิ่งที่องค์กรสนับสนุน ขอบเขต และเงื่อนไขพิจารณาราคา
8. ตรวจรายการที่ขาด → บันทึกร่าง → ส่งตรวจภายใน → ผ่านตรวจภายใน
9. ดูข้อเสนอและพิมพ์/บันทึก PDF จาก browser เมนูและข้อมูลบัญชีจะไม่ถูกพิมพ์

ต้นแบบเป็นกรอบให้ผู้เขียนปรับ ไม่ใช่ระบบตัดสินใจหรือสร้างราคาให้เอง ข้อมูลจากองค์กรถูกนำมาเป็นโจทย์ ไม่ใช้คะแนน Quiz แทนความต้องการอบรม

## ความสัมพันธ์ในการออกแบบ

| ส่วน | สิ่งที่ต้องเชื่อม |
| --- | --- |
| โจทย์องค์กร | ปัญหาจริง → ผลลัพธ์ที่ต้องการในงาน |
| วัตถุประสงค์ | พฤติกรรมที่ผู้เรียนทำได้ → หลักฐานประเมิน |
| กิจกรรม | ขั้นตอนฝึก → ผลงาน → วัตถุประสงค์ที่รองรับ |
| เวลา | ผลรวมกิจกรรม ≤ กรอบเวลาที่กำหนด ไม่รวมพัก |
| การนำไปใช้ | แผนทดลอง → ผู้สนับสนุน → จุดติดตาม |
| ข้อเสนอ | สิ่งส่งมอบ → ขอบเขต → เงื่อนไขและงบประมาณ |

เพิ่ม/ลบวัตถุประสงค์และกิจกรรมได้ การลบวัตถุประสงค์จะลบการอ้างอิงในกิจกรรมด้วย สามารถเลื่อนลำดับกิจกรรมขึ้น/ลง

## ร่างในเครื่องและข้อมูลทีม

- เก็บร่างในเครื่อง: localStorage ของเบราว์เซอร์นั้น มีหนึ่งช่องร่าง ไม่ได้บันทึกบน server
- เปิดร่าง/นำเข้า JSON: สร้างร่างใหม่ ไม่ใช้รหัสหรือฉบับทีมจากไฟล์มาทับของเดิม
- ดาวน์โหลด JSON: สำรองและย้ายร่าง ตรวจรูปแบบและจำกัดขนาดนำเข้า 100KB
- บันทึกในระบบทีม: ต้องเข้าสู่ระบบและได้รับสิทธิ์ server ระบบแจ้งสำเร็จหลัง RPC ยืนยันเท่านั้น
- เปลี่ยนต้นแบบ/เปิดหลักสูตรอื่น/ออกจากระบบ: ถ้ามีการแก้ไขไม่บันทึก จะเตือนก่อนแทนที่
- ปิดหรือโหลดหน้าใหม่ขณะมีการแก้ไข: ใช้ beforeunload เตือนตามความสามารถของ browser

ไฟล์ร่างมีข้อมูลโจทย์องค์กร ผู้ใช้ควรเก็บในอุปกรณ์ทำงานที่เหมาะสม และไม่ใส่ข้อมูลส่วนบุคคลของพนักงานรายอื่น

## การยืนยันตัวตนและสิทธิ์

ส่วนข้อมูลทีมของเครื่องมือนี้ใช้ **Supabase Auth** และ API `/api/course-designs` ตรวจ access token ด้วย `auth.getUser(token)` พร้อมตรวจ email ที่ยืนยันแล้วและอยู่ใน allowlist ฝั่ง server

ไม่เชื่อถือบทบาทหรือชื่อผู้ใช้ใน `choomcham_admin_user` ของระบบเก่า ไม่ใช้รหัสผ่านที่ฝังในโค้ด และไม่ import legacy services client เข้ามาในเครื่องมือนี้

หากยังไม่ตั้งค่า ผู้ใช้ทำได้เฉพาะเขียนต้นแบบและเก็บร่างในเครื่อง API ข้อมูลทีมปฏิเสธคำขอ ไม่เปิดสิทธิ์ผู้ดูแลให้อัตโนมัติ

## ตั้งค่าก่อนใช้งานร่วมกัน

1. ตรวจและรัน `supabase/migrations/20261009_course_designs.sql` ในโครงการ Supabase ที่ใช้จริงผ่านกระบวนการ migration ของทีม
2. สร้างหรือเชิญผู้ดูแลผ่าน Supabase Auth และยืนยันอีเมล ตั้งรหัสผ่านตามระบบ Auth ของโครงการ
3. ตั้งค่า build ฝั่ง client: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` ใช้ public anonymous key เท่านั้น
4. ตั้งค่า Cloudflare Functions: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `COURSE_ADMIN_EMAILS` (อีเมลคั่นด้วย comma)
5. ไม่ใส่ service role ในตัวแปรที่ขึ้นต้น `VITE_` และไม่ commit ค่าจริง
6. ตรวจการเข้าสู่ระบบ โหลด brief บันทึก และอ่านประวัติใน staging ก่อน production

อีเมลต้องมีทั้งบัญชี Auth และอยู่ใน allowlist การเพิ่มอีเมลใน allowlist เพียงอย่างเดียวไม่ได้สร้างบัญชี ผู้ดูแลที่อยู่ในรายการมีสิทธิ์อ่านและแก้ไขหลักสูตรร่วมกันทั้งหมด

## ตารางและการป้องกันเขียนทับ

`course_designs` เก็บฉบับปัจจุบัน และ `course_design_versions` เก็บ snapshot ทุกครั้งที่บันทึก เปิด RLS และปิดสิทธิ์ anon/authenticated ในทั้งสองตาราง เข้าผ่าน server ที่ตรวจสิทธิ์แล้วเท่านั้น

RPC `save_course_design` ใช้ expected version, transaction lock และบันทึก snapshot ในธุรกรรมเดียวกัน ถ้าฉบับเปลี่ยนจะคืนข้อผิดพลาด conflict → API ตอบ 409 ร่างบนหน้าจอยังอยู่ ไม่มีการ overwrite อัตโนมัติ เก็บร่างก่อนโหลดฉบับทีมล่าสุดเพื่อรวมการแก้ไข

การนำเนื้อหาฉบับเก่ากลับมาแก้ไขยังใช้ version ล่าสุดที่โหลด ไม่ย้อนเลขฉบับหรือแก้ snapshot เก่า กดบันทึกแล้วสร้างฉบับใหม่ ผู้บันทึกอ้างอิงจาก user ID ที่ server ตรวจแล้ว

## การตรวจความพร้อม

ร่างบันทึกได้แม้ยังไม่ครบ แต่ REVIEW/APPROVED ต้องมีบริบท จำนวนผู้เรียน วัตถุประสงค์ หลักฐาน กิจกรรมที่รองรับ ผลงาน เวลาที่พอดี แผนวัดผล ผู้รับผิดชอบ สิ่งส่งมอบ ขอบเขตและเงื่อนไขราคา

การแก้เนื้อหาฉบับผ่านตรวจจะกลับเป็นร่าง ข้อเสนอจะแสดง “ผ่านตรวจภายใน” เฉพาะเนื้อหาที่ตรงกับฉบับทีมซึ่งบันทึกสถานะนี้แล้ว สถานะดังกล่าวไม่ใช่การอนุมัติซื้อของลูกค้า หรือการอนุมัติแบบแยกคนเขียน/คนตรวจโดยอัตโนมัติ

## การทดสอบและขอบเขต

- `npm run typecheck`, `npm run build`, `npm run test:courses` และ Cloudflare Functions compile
- Model/API tests: ต้นแบบ 6 โปรแกรม การนำ brief มาใช้ import validation การเชื่อมวัตถุประสงค์ เวลารวม ผู้ดูแลที่ยืนยันแล้ว allowlist สถานะผ่านตรวจ และ version conflict ด้วยระบบจำลอง
- PostgreSQL ทดสอบแบบฝังตัว: migration ฉบับใหม่/ชนกัน snapshot atomic rollback และสิทธิ์ client/history
- Browser QA ด้วย Auth/API จำลอง: ต้นแบบ ร่างในเครื่อง ไฟล์ไม่ถูกต้อง ลบวัตถุประสงค์และ reference, brief, conflict, บันทึกส่งตรวจ, ประวัติ, JSON export และหน้าจอ 1440/768/390/320px

ไม่ได้รัน migration, สร้างบัญชี, บันทึกข้อมูลหรือส่งข้อความใน production ยังไม่ได้แก้ authentication/API รุ่นเก่าของ Admin ทั้งระบบ เครื่องมือนี้ไม่มี AI เขียนหลักสูตรอัตโนมัติ ไม่มีเผยแพร่ Sales page จากร่าง และไม่มีการส่ง Proposal ให้ลูกค้าอัตโนมัติ
