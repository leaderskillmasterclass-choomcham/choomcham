# หลักสูตรองค์กรตัวจริง™ และการออกแบบ Proposal

## โครงสร้างที่นำไปใช้

ข้อมูลกลางอยู่ใน `app/lib/programs.ts` ใช้ร่วมกันใน Sales page รายหลักสูตร กรอบหลักสูตรสำหรับพิมพ์ และแบบฟอร์มขอ Proposal เป็นกรอบออกแบบเบื้องต้น ไม่ใช่หลักสูตรหรือราคาที่ยืนยันแล้ว

| ระดับ | หน้า Sales page | จุดเน้น | ผลงานการเรียนรู้ตั้งต้น |
| --- | --- | --- | --- |
| 1 · REBORN | `/programs/reborn` | จุดแข็ง คุณค่า และบทบาท | Strength Map / Role Canvas / แผน 30 วัน |
| 2 · COMMUNICATION | `/programs/communication` | ฟัง พูด Feedback | Listening Checklist / Conversation Canvas |
| 3 · TEAM | `/programs/team` | Trust เป้าหมายร่วม Ownership | Team Charter / Role Map / Team Experiment |
| 4 · LEADER | `/programs/leader` | โค้ช มอบหมาย พัฒนาทีม | Leadership Plan / Delegation Canvas |
| 5 · CULTURE | `/programs/culture` | Values สู่พฤติกรรมและกิจวัตร | Behavior Playbook / Culture Pilot |
| เรือธง | `/programs/from-zombie-to-living-organization` | เชื่อมคน ทีม ผู้นำ วัฒนธรรม | Learning Journey / แผนทดลอง / Review |

หน้าเรือธงมี 4 โมดูล: REBORN PEOPLE = Level 1, ALIVE TEAM = Levels 2–3, REBORN LEADER = Level 4, LIVING CULTURE = Level 5 ทั้ง 5 ระดับยังมี Sales page แยก ไม่เปลี่ยนโมดูลเรือธงเป็นระดับใหม่

หน้าโปรแกรมรวมและทั้ง 6 Sales page ถูก prerender ตอน build เพื่อให้เนื้อหาและ metadata อยู่ใน HTML ตั้งแต่เปิดหน้า พร้อม canonical แยกและ sitemap ส่วนฟอร์ม/กรอบ Proposal ใช้ noindex

## เส้นทางผู้ใช้

หน้าแรก → รายละเอียดหลักสูตร → `/proposal/request?program=<slug>` → ส่งโจทย์องค์กร → บันทึกใน CRM → ทีมงานยืนยันโจทย์ → ออกแบบ Proposal → ผู้มีอำนาจพิจารณา

ปุ่มระดับทั้ง 5 มีทั้งรายละเอียดและขอ Proposal ส่วนเรือธงมีปุ่มขอโปรแกรมเต็ม แยกจากปุ่มขอเฉพาะโมดูล

`/proposal?programSlug=<slug>` แสดงกรอบหลักสูตรเดียวกับ Sales page พร้อมพิมพ์/บันทึก PDF ไม่มีราคา ตัวเลขผลงาน หรือข้อมูลผู้ติดต่อใน URL ใช้เป็นเอกสารหารือ ไม่ใช่ใบเสนอราคาที่อนุมัติแล้ว เส้นทาง Proposal เดิมยังคงรองรับข้อมูลเก่า

## แบบฟอร์ม Discovery Brief

ข้อมูลจำเป็น: หลักสูตร โจทย์ ผลลัพธ์ที่อยากเห็น กลุ่มผู้เรียน จำนวนผู้เรียน รูปแบบ ระยะเวลา ผู้ติดต่อ องค์กร อีเมล และความยินยอมให้ติดต่อ

ข้อมูลเสริม: ตำแหน่ง โทรศัพท์ ช่วงเวลาที่ต้องการจัด สถานที่ และกรอบงบประมาณ

ใช้ข้อมูลเพื่อยืนยันเป้าหมายที่สังเกตได้ ไม่รวบรวมรายละเอียดส่วนบุคคลของพนักงานรายอื่น ไม่ใช้ผล Zombie Check เป็นการวินิจฉัยทางการแพทย์หรือข้อสรุปแทนข้อมูลทั้งองค์กร

## กรอบออกแบบข้อเสนอเฉพาะองค์กร

1. **Discovery:** สัมภาษณ์ Sponsor/HR ยืนยันปัญหา ผลกระทบทางธุรกิจ กลุ่มเป้าหมาย และข้อจำกัด
2. **Baseline:** เลือกหลักฐานตั้งต้น วิธีรับฟัง และตัวชี้วัดที่องค์กรเข้าถึงได้
3. **Learning architecture:** เลือกระดับ/โมดูล กำหนดวัตถุประสงค์ที่สังเกตได้ และเชื่อมกับโจทย์งาน
4. **Experience design:** วางกิจกรรม การสะท้อนคิด การฝึก และเครื่องมือ พร้อมเวลาและผู้รับผิดชอบ
5. **Transfer:** เลือกงานทดลอง หัวหน้าที่สนับสนุน คู่เรียนรู้ และจุดติดตาม
6. **Evaluation:** แยกความพึงพอใจ ทักษะที่ฝึก พฤติกรรมในงานจริง และผลต่อการทำงาน ไม่ใช้แทนกัน
7. **Commercial scope:** ยืนยันจำนวนรุ่น/ผู้เรียน วันอบรม ทีมวิทยากร สถานที่ ค่าเดินทาง สิ่งส่งมอบ ราคา ภาษี และเงื่อนไข
8. **Approval:** ผู้รับผิดชอบตรวจเนื้อหาและราคา ก่อนส่ง Proposal ให้ลูกค้า

| --- | --- | --- |

| Learning Journey | โมดูล ลำดับ ชั่วโมง วิธีเรียนรู้ | แต่ละกิจกรรมเชื่อมเป้าหมาย |

| งบประมาณ | ค่าวิทยากร ออกแบบ เดินทาง ติดตาม ภาษี | ตรวจราคาและเงื่อนไขก่อนส่ง |

## Backend และ CRM

`POST /api/program-proposal` ตรวจข้อมูลบน server ด้วย validator เดียวกับ client จำกัดความยาว รูปแบบอีเมล จำนวนคน enum หลักสูตร/รูปแบบ/ระยะเวลา และ consent ตรวจ Origin เมื่อมี และ honeypot ไม่สะท้อน error ภายในฐานข้อมูล

บันทึกในตาราง `leads` เดิม: `result_level=PROPOSAL_REQUEST`, `score=0`, `status=NEW` เก็บ `program_slug`, `program_interest`, `schema_version`, `source_page` และ `proposal_brief` ใน `dimensions_scores` จึงไม่ต้องเปลี่ยน schema ฐานข้อมูล ตรวจโครงสร้างตารางจริงก่อน deploy

Endpoint ใช้ `SUPABASE_URL` (หรือ `VITE_SUPABASE_URL`) และ `SUPABASE_SERVICE_ROLE_KEY` จาก environment ฝั่ง server เท่านั้น หากไม่มี config หรือ insert ล้มเหลว จะตอบ 503 และแบบฟอร์มยังแสดงข้อมูลเดิม ไม่สร้าง lead จำลอง ไม่แจ้งสำเร็จ และไม่ส่งข้อมูลไป LINE broadcast หรืออีเมลอัตโนมัติ

CRM แสดง brief และเปิดกรอบหลักสูตรตาม slug สำหรับคำขอใหม่ โดยไม่เติมราคา 185,000 บาทจากเส้นทางเดิม ทีมงานตรวจคำขอจากแท็บ Proposal ใน CRM

## ขอบเขตและงานต่อ

งานนี้สร้าง Sales page การรับ brief และกรอบหลักสูตร ไม่ได้สร้าง PDF เฉพาะองค์กรอัตโนมัติ ระบบอนุมัติราคา การชำระเงิน หรือการส่งข้อความให้ลูกค้า

## การตรวจสอบ

- `npm run typecheck` และ `npm run build`
- `npm run test:programs`: ตรวจ mapping ทั้ง 6 หลักสูตร ขอบเขตการตรวจข้อมูล consent Origin ขนาดข้อมูล และกรณีฐานข้อมูลสำเร็จ/ล้มเหลวด้วยฐานข้อมูลจำลอง
- `npx wrangler pages functions build functions --outdir <temporary-directory>`: ตรวจการ compile Cloudflare Functions
- Browser QA: หน้าหลักสูตรทั้ง 6 หน้า ที่ 1440/768/390/320px ไม่มี horizontal overflow, query เลือกหลักสูตรถูกต้อง, slug ไม่รู้จักไม่เปิดหลักสูตรอื่นแทน, homepage links ครบ, mock ส่งข้อมูลล้มเหลวแล้วแก้ไข/ส่งใหม่ได้, ข้อความสำเร็จมีเลขอ้างอิง, กรอบพิมพ์ซ่อนเมนู และไม่มี page JavaScript errors
- HTML ที่ prerender ทั้ง 7 หน้ามีเนื้อหา title และ canonical หนึ่งรายการ พร้อมตรวจ sitemap XML

การทดสอบไม่ได้เชื่อมต่อฐานข้อมูล production หรือส่งคำขอ/ข้อความจริง ยังต้องตรวจการตั้งค่า environment และการบันทึกลง Supabase จริงใน staging ก่อน deploy

ก่อน production ต้องแก้ประเด็นความปลอดภัยเดิมของระบบ admin/credentials ที่พบในการตรวจครั้งก่อน และตั้งค่าป้องกัน spam/rate limit ที่ Cloudflare ตามปริมาณใช้งานจริง Endpoint นี้ไม่ได้แก้ระบบ auth ของ admin เดิม
